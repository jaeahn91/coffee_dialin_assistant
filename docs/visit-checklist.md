# 파일럿 로스터 방문 체크리스트

> 대상: nlbo커피 (코스타리카 하시엔다 산 이시드로 게이샤 레드허니)
> 목적: (1) 실사용 감상·사용성 관찰, (2) 실데이터로 드러난 신호 확인, (3) 이연된 설계 결정,
>       (4) 로스터 셀프서비스(Phase C) 수요 파악.
> 작성 2026-07-03. 데이터 스냅샷은 아래 "방문 시점 데이터" 참조.

---

## 0. 방문 전 준비

- [ ] **깨끗한 데모 QR 2~3장 발급** — 현 테스트 QR(`gpze`)은 사슬이 이미 온도 90°C까지 내려가
      있어(아래 데이터 참조) 첫인상 데모에 부적합. 프로덕션 base-url로 새로 발급해 깨끗한 사슬에서
      시연. (`scripts/issue-qr.mjs --base-url https://coffee-dialin-assistant.vercel.app`)
- [ ] 프로덕션 라이브 확인 — 디자인 1차·경계 가드 배포됨(2026-07-03 확인). 사장님 폰으로 실제 스캔되게.
- [ ] `report-feedback.mjs` 출력 캡처해 가기 — 사장님께 "이렇게 데이터가 쌓입니다" 보여줄 용도.
- [ ] 라이트/다크 둘 다 보여줄 수 있게(사장님 폰 다크 설정일 수 있음).

## 1. 디자인·사용성 (보여주고 관찰 — 설명 최소화)

먼저 사장님이 **직접 스캔해서 끝까지** 눌러보게 두고, 어디서 멈칫하는지 관찰한다.

- [ ] 새 디자인(웜 뉴트럴 + Pretendard) 첫인상 — 과하지도 밋밋하지도 않은지.
- [ ] 레시피 카드가 한눈에 읽히는지 — 값/라벨 구조, 붓기 스케줄, "지난 피드백 반영" 배지 이해되는지.
- [ ] 질문 문구가 손님 입장에서 자연스러운지 ("맛은 어땠나요?" → 좋아요/괜찮아요/아쉬워요).
- [ ] 처방 한 줄("분쇄도를 곱게" 등)이 **행동으로 옮길 만큼** 구체적인지, 아니면 막연한지.
- [ ] "잘 모르겠어요 — 도움 받기"(챗봇 스텁) 문구가 헛기대를 주지 않는지.

## 2. 실데이터로 확인할 것 (이번 방문의 핵심)

`gpze` QR에 **연속 4회 '아쉬워요'**가 찍혔고, 그중 3회가 `high/short`(온도 높음+추출 짧음)라
시스템이 온도를 **93→92→91→90**으로 계속 낮췄다. 물량은 트리 경로라 270g 그대로.

- [ ] **이 4회가 실제 추출이었나, 그냥 눌러본 테스트였나?** — 이 답에 따라 아래 해석이 갈린다.
- [ ] (실제였다면) **93°C 기준 온도가 이 원두에 높은 것 아닌가?** 같은 방향("온도 높았다")이
      반복됐다는 건 기준 레시피 자체를 손봐야 한다는 신호일 수 있다. → 그 자리에서 기준 온도를
      낮춰 재발행할 수 있음(`publish-recipe`, 방문 전 준비되면).
- [ ] **온도를 1°C씩 낮추는 처방이 실제로 도움이 됐나?** 손님이 개선을 체감했는지, 폭이 너무 작진 않은지.
- [ ] **물량이 270에서 안 움직인 것**에 대한 인상 — 트리 경로(추출시간 이탈)는 온도·분쇄만
      건드리고 물은 안 바꾸는 설계인데, 사장님이 물 조정을 기대했는지.
- [ ] 20뷰 대 4세션 — 스캔은 했지만 질문까지 안 간 이탈이 있다. 손님들이 왜 도중에 멈추는지 짚이는 게 있나.

## 3. 이연된 설계 결정 (ADR-002 목록 + 신규)

- [ ] **언스페셜티 링크 노출 동의** — 카드 하단 "내 분쇄도 측정하기 (언스페셜티 사이트) ↗".
      외부 사이트 링크를 로스터 페이지에 노출해도 괜찮은지 명시적 동의.
- [ ] **그라인더 힌트** — 처방이 "분쇄도를 곱게"처럼 추상적인데, 사장님 그라인더 기준
      "몇 클릭 곱게"로 병기하면 손님이 더 쉬운지. (§9 고정 템플릿 확장 필요 — 그라인더 모델 필요)
- [ ] **조정 후 µm 목표 병기** — 분쇄도를 "약 850µm → 800µm 목표"처럼 수치로 병기할지.
      (현재는 권유 이력만 표시, ADR-002)
- [ ] **분쇄 반복 3회 상한 문구** — "이미 충분히 조정했어요. 로스터리에 문의" 문구가 납득되는지,
      혹은 다른 안내가 나은지. (경계 가드 ADR-003)

## 4. 레시피 운영 — 셀프서비스 수요 파악 (Phase C 착수 판단 근거)

대시보드를 만들지, 컨시어지(내가 대행)로 갈지를 여기서 가른다.

- [ ] **레시피를 얼마나 자주 바꾸고 싶나?** — 로스팅 배치마다? 계절마다? 자주면 셀프서비스 가치 큼.
- [ ] **직접 등록·발급하고 싶나, 요청하면 해주는 방식이 편한가?** — 솔직한 선호.
- [ ] **원두 라인업 규모** — 지금 1종. 여러 종 굴리면 관리 UI 필요성 올라감.
- [ ] **로그인 방식** — 추상적으로 "매직링크 vs 카카오" 묻지 말고 관찰 가능한 두 질문으로:
      (1) 업무용 이메일을 평소 자주 확인하시나요? (아니오 → 매직링크 탈락)
      (2) 이런 관리 화면은 폰으로 보실 것 같나요, 컴퓨터로? (폰 위주면 카카오 가치↑)
      — Supabase Auth는 방식 공존 가능하니 파일럿은 이메일 계열로 시작, 카카오는 확장 단계 투자.

**설계상 확인**: 손님이 다이얼인 진행 중인데 로스터가 레시피를 새로 발행하면 어떻게 보일지 —
    실운영에선 옛 조정 델타를 새 기준에 얹으면 이중 보정이 되므로, 버전이 바뀌면 그 QR 사슬을
    **새 기준에서 다시 시작**("추천 레시피가 새로 나왔어요" 안내 + 깨끗한 카드)하는 방향으로 결정됨
    (NEXT.md Phase C 이연 결정). 사장님께 이 동작이 자연스러운지 한 번 확인.

## 5. QR·인쇄 실무

- [ ] **QR 인쇄·부착은 누가 어떤 형태로?** — 스티커 인쇄소? 매장 프린터? 봉지에 직접?
- [ ] **커스텀 도메인** — 실제 인쇄 직전에만 필요(임계경로 밖). 살 의향 확인됨. 인쇄 일정 잡히면 구매.
- [ ] **봉지 단위 유니크 발급** 방식 설명·동의 — 봉지마다 다른 QR = 재스캔이 곧 같은 봉지의 후속
      추출로 이어져 조정이 누적되는 구조. 사장님 운영과 맞는지.
- [ ] 스티커에 원두명·코드 끝4자 병기 방식 확인(현재 발급 도구 기본값).
