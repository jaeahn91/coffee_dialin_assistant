# ADR-001: 쓰기 경로는 B+ (Server Actions + 기록 RPC + page_view)

날짜: 2026-07-02 · 상태: 채택

## 결정

소비자(QR) 쓰기 경로를 다음 구조로 구현한다.

- **전송**: Next.js Server Actions (내장 origin 보호).
- **검증·처방 재도출**: 서버 TS(`lib/server/derive.ts`) — zod 파싱 후 `flowStep`을
  서버에서 재주행해 경로·처방을 도출한다. 클라이언트가 계산한 처방은 신뢰하지 않고,
  상태머신이 실제로 질문한 답만 채택한다(경로 밖 필드 무시).
- **기록**: Postgres RPC 2개(`start_brew_session`, `record_feedback`,
  `supabase/migrations/0002_rpc.sql`)가 한 트랜잭션에서 §8-5 사슬 연결·일일 상한·
  다중 insert를 원자 처리한다. 도메인 로직(처방 계산·§9 표현)은 SQL에 두지 않는다.
- **퍼널**: `page_view`(스캔) → `brew_session`(첫 답변 시 생성) → `feedback`(완주).
  세션을 첫 답변 시 생성하므로 봇·링크 프리뷰는 page_view까지만 남는다.

## 기각한 대안

- **A안 (다중 insert)**: 비원자 — 부분 실패·사슬 레이스가 §2 지표를 조용히 오염한다.
- **C안 (REST API + 인프라 레이트리밋)**: 소비자가 없는 시점의 계약 동결(닻 효과),
  CSRF 직접 관리, 파일럿 반복 속도 저하. 아래 트리거 전까지 보류.

## C 전환 트리거

- **외부 클라이언트 확정**(네이티브 앱·위젯·서드파티 통합) → route handler 추가, 전면 전환.
- **어뷰즈가 DB 비용이 될 때** → 레이트리밋만 부분 채택(액션 첫 줄 또는 미들웨어/WAF).
  이것만으로는 전면 전환 불필요.

## 씸(seam) 계약 — C 전환을 싸게 유지하는 규율

모든 쓰기는 `lib/`의 타입 있는 함수를 통과한다. server action은 "인자 검증 → lib 호출 →
결과 매핑" 래퍼로만 유지한다(`app/r/[code]/actions.ts`). 이 규율이 지켜지는 한
C 전환 = 같은 lib 함수를 route handler로 한 번 더 감싸는 작업이다.

## 보류된 결정 (첫 외부 소비자가 정보를 준다)

| 결정 | 필요한 정보 |
|---|---|
| API 인증 방식 (API 키 / 서명된 임베드 토큰 / OAuth) | 소비자 유형 |
| URL 구조·버저닝·에러 봉투 규약 | 소비자의 소비 방식 |
| 레이트리밋 등급·정책 | 실트래픽 패턴 |

**안티골**: 소비자 확정 전에 엔드포인트 스펙(OpenAPI 등)을 쓰지 않는다 — 추측 스펙은
닻 효과로 실제 요구를 왜곡한다.

## 이 구현의 알려진 한계 (의도된 파일럿 범위)

- 세션은 방문당 1개, 기록도 1회 — "처음부터"로 재응답해도 재기록하지 않는다
  (다음 추출은 재스캔이 새 세션·새 기록).
- "도움 받기"(bail) 중도이탈은 피드백 미기록 — 챗봇 스텁 단계의 의도된 공백.
- `after_snapshot`의 분쇄는 수치 미적용(§6-4 표현 방식 미결정) — moves에 기호로만 남는다.
- 표시 레시피는 항상 기준(활성) 레시피 — 재스캔 시 직전 조정(after_snapshot) 반영 표시는
  후속 작업(docs/NEXT.md).
- 세션 시작 실패(상한 등) 시 손님 경험 우선: 처방 안내는 그대로 진행하고 기록만 생략한다.
